# 006：将思考开关适配到 GPT

## 出处、目的和此前差异

原教程 docs/05-streaming.md:407 Extended Thinking；python/mini_claude/agent.py:358 模式判断及 :1633 请求构造。原文使用 Anthropic thinking/budget_tokens。005 先复现了它，但用户默认是 GPT-5.5/Codex，开关未作用于实际使用的模型。用户要求改为 GPT 格式，本次明确作为协议适配，不当作原文代码。

已核对官方文档：
- https://developers.openai.com/api/docs/models/gpt-5.5 ：普通版支持 low/high 等档位。
- https://developers.openai.com/api/docs/guides/reasoning ：Responses 使用 reasoning.effort。
- https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create ：Chat Completions 使用 reasoning_effort；max_completion_tokens 包含回答和推理 token。

## 用人话理解

我们不是自己编写模型的思考过程，只是在任务单上写“这次请多花一点精力分析”。不带 --thinking 使用 low；带 --thinking 使用 high。low 也可以思考，不代表关闭推理。low/high 是本项目选择的默认映射，不是官方规定的 CLI 开关，更不是精确秒数或 token 数，也不能保证 high 每次都更好。

## 一、main.py：识别你的启动选项

`thinking = "--thinking" in argv`：in 检查列表里有没有这个字符串，结果是 True 或 False。

`argv = [argument for argument in argv if argument != "--thinking"]`：列表推导式，保留不是开关的参数，让开关不混进用户问题。

`run_agent(..., thinking=True)` → `ask_model(..., thinking=True)`：用关键字参数把同一个值传给下一层；不带选项时默认值 False。所有工具后的后续模型请求仍使用同一选择。本次更新启动提示，避免再显示“仅 Anthropic”。

## 二、thinking.py：把布尔值翻译成 GPT 档位

```python
def get_gpt_reasoning_effort(thinking=False):
    return "high" if thinking else "low"
```

`def` 定义函数；`thinking=False` 表示不传参数时默认 False；`return` 返回一个值。最后一行是条件表达式，等价于：

```python
if thinking:
    return "high"
else:
    return "low"
```

原有 Anthropic 函数保留，供双后端对应路径使用；默认 GPT 请求不走 Claude 模型名称判断。

## 三、codex_backend.py：把档位放进默认请求

```python
"reasoning": {"effort": get_gpt_reasoning_effort(thinking)}
```

这是嵌套字典。外层键 reasoning 对应一个小字典，小字典的键 effort 对应 low 或 high。函数先算出字符串，再放进字典，send_request 将整个字典转成 JSON 发出去。

不带开关时：`{"reasoning": {"effort": "low"}}`。
带开关时：`{"reasoning": {"effort": "high"}}`。

ask_model 中的 lambda 把开关也交给每一次重试，重试不会回到 low。

## 四、api_backends.py：官方 API 的字段写法

同样调用 GPT，协议不同，字段名不同：

| 路径 | 发出的思考字段 |
| --- | --- |
| 默认 Codex，Responses 风格 | reasoning: {effort: high} |
| OpenAI Chat Completions | reasoning_effort: high |
| Anthropic 原教程 | thinking: {type: enabled, budget_tokens: ...} |

backend 的 openai 分支把 thinking=True 转交 call_openai。GPT-5.5 的 generation_options 字典放 reasoning_effort 和 max_completion_tokens，`**generation_options` 把字典展开成 SDK 的命名参数。

max_completion_tokens=16384 是回答加推理的总上限，保留现有请求总额度，不是“固定思考 16384 个 token”。此上限可能导致复杂问题提前耗尽额度，原有完整结束检查会报错而不执行不完整工具请求。

GPT-5.5 不再使用旧 max_tokens 字段。其他兼容模型在未开启时保留原格式；显式开启且不是本次核对的普通 gpt-5.5/日期快照时清楚报错，避免猜测全部模型都接受相同参数。Pro 和未知别名不在此次适配范围。

## 五、回复与工具怎么处理

GPT 的 reasoning 和 Anthropic thinking 内容不是同一种结构。Codex 继续保留原有 reasoning.encrypted_content，完整输出进入历史供下一次请求使用，不解密、不显示为模型私有思考文字。不能照搬 Anthropic 的过滤方式将 Codex reasoning 项删除。

文字仍流式显示；完整工具请求仍等请求结束后由 run_agent 执行。这次只改变请求配置，不改变工具名、参数或执行行为。

## 完整流程与直接测试

`python main.py --thinking` → argv 含开关 → thinking=True → run_agent → ask_model（包括重试）→ reasoning.effort=high → Codex 后端 → 完整回答/工具请求 → 原有 Agent 循环。

在项目目录执行 `python main.py --thinking`，直接问“读取 main.py，逐步解释这个 Agent 如何调用工具”。普通强度执行 `python main.py`。这里只是不同的请求档位；不能单靠模型说“我使用高强度”证明生效，应检查程序发出的参数。
